# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Greatforge is a worldbuilding app (React 19 + TypeScript + Vite, Firebase behind a repository seam). The shipped module is a **spell workshop**; a conlang module is planned and should reuse the same storage seam.

`README.md` is still the untouched Vite template — ignore it.

## Commands

```
npm run dev        # Vite dev server on :5173
npm run emulators  # Firebase auth (:9099) + Firestore (:8080) + UI (:4000)
npm run build      # tsc -b && vite build — this is the typecheck
npm run lint       # eslint .
```

There is **no test runner and no test files**. `npm run build` plus `npm run lint` are the only automated checks; behavioural changes to the reaction resolver are verified by driving the app in a browser, or by `sim/balance.ts` (kept out of `tsconfig`, see "Balance") or another throwaway Node script that imports `lib/reaction.ts` directly. Nothing on this machine runs TypeScript directly — compile such a script out of the tree with `npx tsc <file>.ts --ignoreConfig --outDir <scratch> --module commonjs --target es2022 --moduleResolution node --skipLibCheck --ignoreDeprecations 6.0` and run the emitted `.js` under node.

Setup: copy `.env.example` to `.env.local`. `VITE_USE_FIREBASE_EMULATOR=true` points auth and Firestore at the local emulator suite; the real `greatforge` project's config goes in the same file with the flag off. `.env.local` is gitignored.

## Architecture

Four layers, strictly one-directional (`types` ← `data`/`lib` ← `state` ← `components`):

- **`src/types/worldbuilding.ts`** — the domain. Currencies, `Ledger`, `MaterialComponent`, `Spell`, `Placement`, the ring constants (`RING_SLOT_COUNT`, the three `TRANSIT_LOSS_*` values, `MAX_LEDGER_ENTRY`), `CasterLevel` and `LEVEL_POWER`, `LossRelief` with `transitScale` / `completionFactor`, and the normalizers. No React, no storage. `Placement` lives here rather than beside the resolver because a form's condition is a question about the ring, and the conditions are written in `data/`.
- **`src/data/currencies.ts`** — currency metadata (labels, hues, prose for vent/toll), the eight `LAWS`, and `describeRole` / `isRelay` / `isInert`. **Roles are derived from the ledgers, never stored**, so an edited component is re-labelled the moment its numbers change.
- **`src/data/spellForms.ts`** — `FORM_META`: what each of the seven forms does to the resolver, and the prose stating it. Imports `describeRole` from `currencies.ts`; imported by `reaction.ts`.
- **`src/lib/reaction.ts`** — `computeReaction(placements, form, level)`, the pure resolver. Walks the eight slots clockwise from slot I, closes the ring, and returns `manifestation` / `toll` / `bled` plus per-slot reports and `carrying`, what is still in flight leaving each slot, which is what `SpellCircle` draws its flow arcs from. `level` defaults to 5 (full power) so every existing call site not about a specific caster reads the whole catalog.
- **`src/lib/repository.ts`** — `WorkshopRepository`, the storage seam. `firestoreRepository.ts` is the only implementation; `WorkshopProvider` takes one as an overridable prop.
- **`src/state/`** — two contexts. `WorkshopProvider` owns components, spells, the unsaved `draft` spell, and derives `placements`/`reaction` via `useMemo`. `DragProvider` implements pointer-based dragging (native HTML5 drag was rejected — its drag image lags the cursor).
- **`src/components/`** — presentational; all state comes from `useWorkshop()` / `useDrag()` / `useAuth()`.

`App.tsx` gates the whole workshop behind Google sign-in and keys `WorkshopProvider` by `user.uid` so switching accounts remounts rather than leaking the previous codex.

### The bench has two modes

`WorkshopProvider.mode` is `'view'` or `'edit'`. **An inscribed working opens in `view`** — `selectSpell` sets it, and `editDraft` (the book's Edit button) is the only way out. `newSpell` and a deleted-out-from-under draft go to `'edit'`; a successful `saveDraft` returns to `'view'`, which is what closes the round trip.

In `view` the book is a written page rather than a form: `Spellbook` renders `BookView`, which shows the title, a form-and-count subtitle, the notes and the text as prose. **No field carries its name there** — what separates notes from text is the page and the typeface, which is how the two already differ. The circle's slots render as `div`s with `role="img"` instead of buttons and drop their `data-slot-index`, so they leave the tab order and a drag finds no target; the codex still reads and its components are still editable, but nothing in it can be armed.

A viewed slot collapses to the round 58px token an empty slot already is, and carries a sigil instead of a name and a ledger. The card is wide because it holds words; a token holds none, so the ring becomes eight of one shape and the flow arcs are the loudest thing on the circle.

`RoleSigil` draws the role in the reagent's own hue: a rayed disc for a source, the ascending triangle for a fuel, two triangles point to point for a converter, a ring with a bar through it for a relay, a descending triangle over a floor for a sink. **The sigils are keyed by `describeRole`, never by material.** Roles are derived from the ledgers, so a reagent the user writes or retunes gets the right glyph with nothing to add to a catalog, and a glyph per material would have nothing to draw for a component that was not seeded. The role is spelled out in the token's `aria-label`, because a glyph standing in for a word is only readable if something says the word.

The names are engraved on a band around the outside of the circle (`namePath`, `.circle__name`), each centred on its own slot's angle. Three things about it are load-bearing:

- **`NAME_RADIUS` is set for the small end of the size range.** The tokens are a fixed 58px whatever size the stage is drawn at, so how far out they reach *in stage units* depends on how big the circle is: wider on a small stage, narrower on a large one. A band tuned for a wide desk runs under the tokens on a narrow one. It reads a little airy at 820px, which is the right way round to be wrong.
- **The band sits outside the viewBox, and only renders because `.circle__engraving` carries `overflow: visible`.** Radius 56 is past the 50 the box clips at.
- **A name on the lower half of the rim is drawn along the anticlockwise arc**, or it hangs upside down. Reversing the path throws the glyphs to the other side of the baseline, so those arcs take a radius one line larger to put the whole band back on one circle.

Per-token inscriptions, curving around each 58px token instead, were tried and dropped. They needed their own SVG per slot measured in pixels rather than stage units, and had to be flung outward from the circle's centre to stay off the flow ring, which passes within a few pixels of every token.

`patchSlots` and `updateDraft` both refuse to run in `view`. That is deliberate belt-and-braces: a pointer press that began before the mode changed can still release over the circle, so the refusal lives in the state and not only in the markup.

### The magic system is load-bearing

It is a hard magic system: `computeReaction` is authoritative about what a spell does, and the `LAWS` array in `data/currencies.ts` is rendered in the UI as the player-facing statement of exactly what the resolver does. **Changing a resolver rule means editing `LAWS` in the same change**, or the app is lying to the user.

Five rules that look arbitrary and are not — each was derived, and reverting one silently breaks balance:

- **Transit loss is a flat amount off the current as a whole**: four units to leap a gap, two across an ordinary reagent (see `crossInto`). Not per parcel, and — since August 2026 — not per currency either. Per-currency charging priced the *breadth* of a spell rather than its shape: a five-currency ring paid five times what a one-currency ring paid for the same walk, and every small flow was erased before the mouth. Per-parcel charging is worse again, making any partial draw evaporate twice as fast.
- **The crossing is charged to the current the destination demanded, and only what that cannot cover falls on the oldest in flight.** A leap over a hole is billed to the slot it is aimed at (`destinationOf`), not to the hole, so three crossings over two holes are paid by the one reagent waiting at the end of them. Billing the oldest outright — the rule until this change — made an arc's loss depend on a reagent with nothing to do with it: a source at slot I is the oldest current for the whole lap, so it absorbed every crossing until it was spent and everything downstream travelled free. A ring of weight I / fulgurite III / black powder VI delivered 7 heat across two holes and a reagent, where the same ring without the source delivered 2. That is unreadable on the circle — the arc says 7 and the five units are bled elsewhere, under another currency.

  **The fallback is not optional.** Without it a crossing whose destination demands nothing in flight costs nothing, which frees gaps entirely (the relay probe goes to 10 vs 9) and lets a lone source ride the whole ring untouched — the same bug from the other end. With it the cost is never waived, only reassigned, which is why the change is nearly balance-neutral: manifestation moved 42.8 → 43.5 at eight reagents, bled is unchanged at 6.5, the fed cohort is unchanged, and every currency stays in band. `transitPayerProbe` asserts both halves.

  **The remainder used to fall to the oldest parcel outright; it now spreads across everything still in flight, in proportion to what each parcel carries, with the unrounded remainder banked as debt rather than dropped.** Oldest-first paid the same defect one step further down: a run of holes with nothing demanded ahead of them drained whichever parcel had been released first to zero before touching any other, so an arc's survival still turned on release order rather than on the crossing itself. A litany of weight I, amber II, fulgurite IV, slow match V used to cross three open slots and the closing lap on Fulgurite's spent heat and light alone, so Slow Match's own heat — released last — reached the mouth as 9, untouched, though nothing about the slot demanded that outcome. A flat proportional split without memory traded one bias for another: a crossing's toll is one or two units split across every parcel in flight, so any one parcel's exact share is usually under a unit and rounds to nothing, which taxes whichever parcel is currently largest every single time and lets every smaller one ride free indefinitely — the same reagent that had been shielded before was now shielded for the opposite reason. `Parcel.debt` fixes that: a parcel's unrounded share is added to what it already owed, and only once the running total clears a whole unit is it actually taken, so a small parcel still pays once enough crossings have accumulated its due, and a large one is not singled out simply for being the only one big enough to round up on its own. Under debt, that same litany delivers heat 8 / motion 1 / light 3 rather than heat 9 / motion 2 / light 3 — the leftover motion finally gets billed instead of dodging every crossing. Both changes together are nearly balance-neutral: manifestation moves 43.5 → 43.4 at eight reagents, bled is unchanged, and every currency still reaches the mouth, in a band that widens slightly to 15–25%. `crossInto` names the two passes for this: `spend` for the destination's own demand, `spendProportional` for what is left.
- **A relay is an ordinary reagent but for one thing: the current crosses it for nothing, wherever it stands.** That one line in `baseTransitCost` is the entire role, and it is the only place in `computeReaction` that asks what a component is. Everything else about a relay is resolved exactly like any other reagent — it is asked for its demands, billed in full for what the ring could not give it, releases its whole yield, and closes its slot.

  The free crossing is unconditional, holes on both sides included. A source at slot II and a relay at slot IV with a gap between them costs 2, where an ordinary reagent at slot IV costs 3: the hole is charged as the hole, and the relay adds nothing on top. `relayProbe` in the harness asserts exactly that pair of numbers using two synthetic reagents with identical demands, one a relay and one a converter, so it cannot drift with the catalog.

  **What qualifies as a relay is decided by `ledgersMatch`, and the test is exact — the two ledgers must agree to the unit, currency by currency.** It used to compare only which currencies each side *mentioned*, which ignored the amounts and so handed the free crossing to two things that are not relays: a reagent giving back more of the same currency than it took (heat 8 for heat 12 — half again, and under the strict 1.5x fuel bar, so it fell through to the relay branch), and a reagent genuinely trading across the same pair of currencies (heat 1 and motion 12 for heat 12 and motion 1, which converts eleven motion into eleven heat). Both were labelled relays in the tray and the editor under a hint that says a relay adds nothing of its own, and both crossed for free. The balance cost was bounded — the crossing is worth one lap, 8 units, so a ring of the fattest legal "relay" netted 160 against 152 for the same reagent one unit dearer — but `isRelay` is the only question the resolver asks about a component, so a wrong answer has teeth rather than being cosmetic. Tightening it changed 0 of the catalog reagents and left every number in the Balance table byte-identical.

  A reagent that profits without giving anything up is a fuel however slim the margin (`givesUpNothing`, checked before the 1.5x ratio), so heat 8 for heat 12 reads as a weak fuel rather than a "converter" that converts nothing. The ratio now only ever decides between fuel and converter for reagents that *did* give something up.

  **What keeps that honest is that a relay is billed like anything else,** and it did not used to be: its demand was a *rating* rather than a requirement, so an underfed relay was never charged, and it handed on only what it actually took. The rating exemption was the bug. A relay dropped into a far-off hole raised `completion` and could not be charged for the demand it then failed to meet, so it was free profit — two of them took a four-reagent ring from 8 delivered to 14 with the toll unmoved at 7, where a starving fuel in the same slot took the toll from 0 to 5. Billing it like anything else fixes that at the root: padding a sparse ring now gains 12.6 manifestation and pays 11.5 toll for it, and there is no ring in 4000 where a starved relay is still free.

  Two other fixes were tried first and both are wrong, for the same reason: conditioning the free crossing on the neighbours, and excluding an isolated relay from `completion` or making it inert. They close the numbers but they make relays look broken in the app — an inert relay draws no arcs and reads as a reagent that refuses to connect, and a conditional crossing makes the same relay cost different amounts in different slots for no reason the player can see. **Keep the special-casing to the one line.**
- **A circle admits each material once, and never more than one source** (law 5) — `placeComponent` lifts a reagent from any slot it already occupies, and does the same to whichever source is standing when a second one is set down. With repeats allowed the optimal ring for every objective is eight copies of one source; the material rule alone doesn't close that, since the catalog's several sources are each a *different* material. A source demands nothing, so it never competes for a slot and never costs a toll, and a crossing's cost is flat per crossing rather than per parcel — stacking sources only ever adds free current, for nothing back. Built into the same otherwise-fed ring, 1/2/3/4 sources delivered 46/58/56/76 manifestation, toll zero throughout; capping the ring to one closes that off. Law 5's last clause, that a reagent is asked only once, used to be bent by the litany's second lap; nothing bends it now, so the ring is walked exactly once in every casting.
- **`completion` is apportioned across the currencies by largest remainder**, not by rounding each one on its own. Per-currency `Math.round` rounds half *up* once per currency in flight, so a wide ring delivered more than the share law 4 states and the overshoot grew with the ring's *width* — the wrong axis entirely for a rule about how closed the ring is. A four-reagent ring holding 3/5/5/5/5 delivered 14 where half is 11.5. Rounding the total once and giving the leftover units to the largest fractional parts holds the error to half a unit for the whole ring at any width. It is worth ~2% of average manifestation on random rings and much more than that on the wide sparse ones, and it is invisible to the conservation check, which balances either way.

**Unmet demand is the only thing the caster is ever charged for.** There is no per-casting cost on top of it (`SPEAKING_TOLL`/`BEND_TOLL` is gone), so a ring that feeds every reagent standing in it is free to speak however large it is — 100% of fully fed rings cost zero, under every form. A measuring form charges nothing at all, ever, because it takes the difference out of the yield instead. Law 6 says both halves in as many words; anything new that bills the body means editing law 6 in the same change.

The catalog in `data/seedComponents.ts` is tuned against these numbers: every currency circulates in an 8–18 band (doubled from 4–9 alongside caster level — see below). It stocks three sinks (Lampblack, Glauber's Salt, Fuller's Earth), added with the forms — a dirge is spared both losses only while a sink stands in the ring *and* its demand is fully met, and the role had deliberately shipped empty until then. Retuning a seed's ledgers without re-checking the frontier is still how a currency goes dead.

**August 2026: only seven reagents in the whole catalog — three sources, four fuels — never cost anything to place, and that is one short of a full ring.** Before this every fuel and converter handed back more than it took, so an eight-reagent working could be built by reading only the slot immediately behind the one being filled and grabbing anything that fit its colour: `sim/balance.ts`'s `naiveChainProbe` found that heuristic reached a toll-free ring on every single attempt, at output matching the deliberate `fedRing` search elsewhere in the harness. Carelessness was not a worse strategy, just a faster one. The fix was not to bill a fully fed ring — law 6 still means a ring that feeds everything standing in it speaks for free — but to make that state harder to fall into by accident: fuels were cut from seven to four, and most of what used to stand under "Converters" now costs more than it returns. A full ring is left needing at least one converter and usually several, and only six of them (four listed with the converters, plus Frankincense and Silt Trap, repriced back into profit to give mass two independent routes) are worth the slot. `naiveChainProbe` is a permanent regression check on this — its toll-free rate must stay well under what a shrug used to buy — and it is why the numbers below read lower than they used to: a lap still costs 8 units in total rather than 8 of *each* currency, but the catalog can no longer be threaded on autopilot to outrun that cost.

**Frankincense and Silt Trap were repriced together, not separately, so mass would not come down to one card.** `LEVEL_POWER` rounds a demand and a yield independently, and Frankincense's original margin (heat 14 → mass 16, +2) rounded to an exact break-even at level one: demand `round(14 × 0.4)` and yield `round(16 × 0.4)` both land on 6. Widening Frankincense alone would have fixed that reagent but made mass-reaching converters depend on a single card, which is worse than the problem it solves — the elegy in particular, which forbids a source and so cannot lean on one to paper over a starved conversion, would still have exactly one non-rare way to touch mass. Silt Trap (motion 14 → mass 12, previously a loss) was repriced to motion 12 → mass 14 in the same change, giving mass two independent low-level-survivable routes from two different feeding currencies (heat and motion) rather than one wider one. Both margins now clear rounding at every level; `naiveChainProbe` still reads 0% toll-free with both in the pool.

### Spell forms are behavioural

`computeReaction` takes a form as its second argument and reads it. (Its third argument, `level`, is a different and much narrower input — see "Caster level" below.) Every form shares two mechanisms; a met elegy has one narrow, capped exception:

- **`underfed: 'credit' | 'measure'`** — what a reagent does when the ring did not meet its demands. `credit` releases the whole yield and bills the caster the shortfall (the old, and only, behaviour). `measure` releases the share of the yield the ring actually fed it, rounded down, and charges nothing. **A measuring form resolves every possible ring at a toll of exactly zero**, which the harness asserts. **The UI never says `credit` or `measure`: the two settings are named *volatile* and *stable* (`UNDERFED_LABEL`)**, in the reaction panel and in law 6. The form picker's options carry the form's name alone. The union keeps the resolver's words, which name the settlement the walk branches on. **The prose behind a name is hover text**, not a line beside it: `UNDERFED_RULE` hangs off the setting's name and `gloss` off the form's, using the plain `title` attribute the tray and the slots already use. The condition stays on the page, because it is a verdict on the ring as placed and changes as reagents move.
- **`condition`** — one stated requirement on the ring, `null` for the prayer. Met, the named loss (or losses) is *spared*; unmet, that same loss is *doubled*. The losses are `transit` (a crossing costs 0, or 4/2 instead of 2/1), `spill` (`completionFactor` returns 1, or squares the share), and `both`. No form spares `spill` alone: dirge and elegy price `both` against a harder-than-usual bar, litany and benediction price it because a `spill`-only condition costs nothing to dodge — see below.

**A met elegy turns some toll into force.** After its first unavoidable wound, every three further toll adds one manifestation, capped at eight. The bonus follows the manifestation's existing currency mix and is recorded separately on the reaction, so the conservation check can distinguish caster-borne grief from current released by reagents. There is still no fourth `LossRelief`: `both` only ever waives or doubles transit and spill. No other form can spare a *toll*.

| form | underfed | condition | spares / doubles |
| --- | --- | --- | --- |
| prayer | credit | — (asks nothing) | — |
| elegy | credit | slot I empty, no source in the ring | both, plus capped grief |
| litany | credit | at least two relays stand in the ring | both |
| dirge | credit | a sink stands in the ring, and its demand is fully met | both |
| invocation | credit | every slot filled | transit |
| ward | measure | slots I and VIII filled, at least two slots empty | transit |
| benediction | measure | three reagents or fewer | both |

Eight things here look arbitrary and are not:

- **The share a measuring form releases is proportional, not binary.** The first cut had an underfed reagent not react at all. Feeding a reagent to the exact unit is rare, so the rule was switched off almost always and the measuring forms of the day were dead: on rings answering their own conditions the dirge delivered 1.2 and the ward 3.2, where the same rings spoken as a prayer delivered 21.0 and 22.4.
- **The ward's condition keeps it off the invocation's ground, and has had to be tightened twice to actually do that.** Without any open clause a full ring satisfies both, and the ward — which measures, and so can never be tolled — strictly dominates the form built for the closed circle. The first cut asked for a single empty slot, which kept the letter of that rule while missing its point: a ring built to feed seven reagents and leave one open came in barely below invocation's own fed ceiling (40.6 against 46.9 at eight, on the same catalog), never risking the toll invocation's `credit` can lose. One slot was not a sacrifice, so the ward beat every other form almost everywhere it was legal rather than only at the threshold it was named for.

  Asking for the ring to be mostly empty over-corrected the other way. Slot I fires before anything has crossed into the ring, so it always receives nothing on the first pass — a tax the ward cannot avoid, since its threshold names slot I by design, but that a form free to place anywhere (the benediction) simply doesn't pay by clustering its reagents away from it. With the condition capped at three reagents, the ward's own two forced slots ate most of that budget: its ceiling over every legal placement topped out at 17 regardless of where the third reagent went, where the benediction, choosing its three slots freely and clustering them just before the ring closes, reached 38 — the ward was then the one being strictly dominated. **At least two slots empty** rather than a bare majority gives the ward room to spend more than one reagent buying real output around its two fixed posts: its ceiling climbs to 45 at six reagents (two genuine gaps, not one), clearing the benediction's 38 while staying well under the invocation's 66 and short of the near-parity with invocation's fed ceiling the one-slot version had. On its own ground against the prayer it now reads 26.9 against 14.5.
- **Elegy's condition spares transit as well as spill, not spill alone — it shipped as `spill` only, and that left the form's central problem unsolved.** No source anywhere means the first reagent the current reaches always starves, so elegy can never be fed and always pays some toll by construction; sparing only the spill still charged the full lap's transit cost on top of that guaranteed toll, so every other reagent in the ring also had to outrun a real crossing cost just to contribute anything net. Moved to `loss: 'both'`: the condition is structural (no source, slot I clear) and holds for the whole ring or not at all, never partially, so meeting it makes every crossing free for the rest of the lap. The fixed price is the one starved slot; nothing downstream of it is taxed again to reach the mouth. On rings that satisfy the condition, elegy now reads 29.7 manifestation against the same ring's prayer at 8.6, at a slightly lower toll than the prayer pays on that ring (33.2 vs 35.2) — a form that can never be fed still has to buy its relief with a fixed price rather than an earned one, the same reasoning dirge's `both` runs on, applied to a bar that is guaranteed rather than built for.
- **Litany's condition names a role instead of a shape.** It used to ask for the reagents to stand in matched pairs — every unbroken run exactly two long, more than one run — and that shape has a hard ceiling on an eight-slot ring: two pairs and the one gap required between each take six slots, and a third pair needs a ninth that doesn't exist, so the rule could never seat more than four reagents, however it was arranged. A form whose reward is a spared spill is only worth anything on a ring with holes in it, but four reagents was the *most* holes litany's own shape ever let a caster reach for, and it never got near the width the other forms draw output from: on the global sweep across every form and ring width, litany won `loud` on 1% of rings and `cheap` on none.

  **At least two relays stand in the ring** replaces the shape with a role, and the role was sitting in the flavour text already: "said through twice, whoever else is present says the second pass" describes an echo, and a relay gives back exactly what it was handed, unit for unit — the mechanical definition of an echo, and the same "twice" the old condition also reached for. Nothing about the rest of the ring is constrained, so the other six slots pack as densely as any other form's, and the catalog carries six relays at common and uncommon rarity, so finding two is a real choice rather than a coin flip a shape used to force.

  **The condition shipped `spill` alone, and a genuinely optimizing caster ignored it.** Sparing or doubling spill does nothing once the ring is closed — a full ring never spills regardless of the condition — so a caster could satisfy litany's letter by placing two relays, or dodge it entirely and just fill the ring, for the identical output. Hill-climbing the true frontier (`sim/generateNearOptimal.ts`, not the random/built sampling elsewhere in the harness) makes this concrete: of litany's 10 best rings by manifestation minus toll, only 3 actually seated two relays — the other 7 were plain closed rings tied with the prayer's own ceiling, at 46 net, without a single relay between them. Moved to `loss: 'both'` with `reward: 'halved'` (two relays is a far easier bar than invocation's full ring, so it earns half the invocation's prize rather than all of it, the same reasoning the ward's halved transit runs on): now every one of the 10 best rings seats two relays, and the ceiling itself climbs, to 52 net, because leaning into the condition is no longer merely harmless — it pays. On its own ground the fed cohort moved from 16.5 against the same ring's prayer at 15.9 (a thin, artefact-driven edge — see below) to 26.9 against 20.4, a real one; the careless cohort moved from 50.3/42.3 to 50.9/42.8.
- **Benediction had the identical bug, worse.** `spill` alone meant a caster could beat the honest three-reagent build by ignoring the cap and filling the ring instead: on the same hill-climbed frontier, benediction's top-ranked ring under the old condition was an 8-reagent ring that failed its own "three reagents or fewer" test outright, at 34 net, while the two rings that actually obeyed the cap topped out at 26 — obeying the form's own rule cost about 25%. Moved to `loss: 'both'`, matching litany: now every one of the 10 best rings is three reagents or fewer, and the frontier is flat at 30 net across all ten — the small-circle identity is no longer dominated by simply not building small. The fed cohort moved from 3.2 against the same ring's prayer at 0.6 to 21.1 against 1.5; the careless cohort from 0.4/2.6 to 8.9/2.4.
- **Dirge's condition asks that the sink's demand be met, not merely present, and needed two changes to make that mean anything.** The old bar — any sink standing anywhere in the ring — was hollow: a sink releases nothing whether it is fed or not, so a hungry one cost nothing beyond its own shortfall either way, and the dirge was spared the spill regardless of whether the ring had done anything for it. Requiring the demand be met in full is a real bar: both sinks in the catalog demand most of a source's whole yield in one currency, so satisfying one takes a ring built around it rather than a slot dropped in passing. It is priced like the harder bar it is — meeting it now spares *both* the spill and the transit, and missing it doubles both (`loss: 'both'`, which elegy, litany and benediction also use, each for a different reason — see the seventh law and `FormCondition.loss` in `spellForms.ts`).

  Deciding "met" without the resolver chasing its own tail took a change to what a condition is allowed to read. Every other condition is a pure question about placements, answered before the ring is ever walked — the walk needs to know what it spares before the first crossing. "Was the sink fed" is a question about the walk's *output*, which does not exist yet when the condition is asked. `ConditionContext.fedUnderBaseline` (`lib/reaction.ts`) breaks the circularity rather than chasing a fixed point: it resolves the same ring once under the prayer — the plain, unblessed rules — and the sink's fate there is the verdict, so the blessing is earned on the ring as it would run unblessed and never on itself. Built lazily inside `computeReaction`, so the other six forms, whose conditions never ask, never pay for the extra walk.

  **That baseline resolves `pessimistic`, rounding a demand up and a yield or transit cost down instead of to the nearest unit — the only place in the resolver that does.** Every quantity `LEVEL_POWER`/`TRANSIT_POWER` scale is rounded independently, and nearest-rounding several of them at once for the same verdict let a ring genuinely a fraction of a unit short of feeding its sink read met at one level and unmet at the next with no trend between them: weight I, charcoal II, Glauber's Salt III, pitchblende IV, bismuth VIII read fed at levels 1 and 3 and starved at 2 and 4, on a sink truly 0.3 heat short at every level below 5. Rounding the demand up and the supply down can only ever fail a ring the caster's true power hasn't reached yet — never pass one by luck — so the verdict now only moves one way as level rises; the same ring reads unmet at 1–4 and met only at 5. `pessimistic` is a parameter on `computeReaction` rather than a second code path, but it is not player-facing and no other call site should ever pass it: applied to a whole eight-reagent working rather than one sink's supply chain, the compounding rounding is heavy enough to read as a real balance cut (`sim/balance.ts`'s fully-fed level-one ring went from ~1% dead to 100%), which is why every ordinary casting still resolves at the nearest unit exactly as before.

  The first cut left `underfed` at `measure`, and that was wrong in a way the harness caught immediately: `measure` charges nothing for a shortfall *anywhere*, not only at the sink, so a ring built to feed the sink exactly and starve every other slot on purpose still collected the full double boon for free — every other reagent's shortfall was free by the same rule that was supposed to make the sink's shortfall free. The condition asks for real commitment across the whole ring; `measure` was refusing to bill the ring for withholding it everywhere else. Moving dirge to `underfed: 'credit'` closes that: every shortfall bills the caster now, the sink included, so the only ring that actually holds the toll at zero is one fed throughout, not one that starves everything but the slot the condition names. Law 6 lists dirge among the volatile forms now rather than the stable ones. Dirge's fed-ground ceiling is unchanged by the fix (32.6 against the same ring's prayer at 14.0, second only to invocation's 46.5) — a truly fed ring has no shortfall for `credit` to bill, so the two rules agree there; they only disagree on a ring that is not, which is the ring the fix exists for. On the careless cohort dirge now reads a toll of 47.6 rather than 0.
- **`spill: doubled` squares the share rather than halving it,** so the forfeit is nil on a closed ring and severe on a sparse one. It stays pointed at the shape the form asked for instead of at the size of the working.
- **Rotations and reflections were considered and rejected.** Starting the walk at another slot, or running it anticlockwise, is a *symmetry of the ring*: indistinguishable from rotating or mirroring the reagents the caster placed. It would read as a rule while adding no decision at all.

`SpellFormMeta` keeps flavour and mechanics in separate fields on purpose. `gloss` is the occasion and the manner, in-world, **no mechanics**; `condition.statement` is the rule, plainly stated, **no atmosphere**, and it must be exactly what `condition.test` checks. `UNDERFED_RULE` states the other half. Writing the mechanic into `gloss` too is how the two drift apart and the app starts lying.

`condition.slots` is the third face of the same sentence: the slots the statement speaks about, washed pale gilt on the circle (`.slot--named`) whether the condition holds or not. It names the same slots the sentence does — slot I and the sources for an elegy, slots I and VIII for a ward, the relays themselves for a litany, the sink for a dirge, and every reagent or every slot for the two that measure the ring's shape outright (benediction, invocation) — so a new condition means writing all three of `statement`, `test` and `slots` together. `conditionSlots` returns nothing for a cold circle, matching `conditionRelief`: an empty ring is not failing its form. The mark is gilt and never red — red is unmet demand alone, and a reagent washed in it reads as starved when the form has only pointed at it — and it is a fill rather than an edge, which is where `.slot--starved` lives. A dirge names its sink slots whether or not the demand there was actually met — the mark says what the rule is looking at, not the verdict, which is what `LOSS_RELIEF_RULE` and the panel's condition heading are for.

**There are seven laws again.** Law 6 forked into the credit/measure settlement, law 7 (**A form asks one thing, and changes only what it names**) bounds what a form may do, and laws 2 and 4 each gained a clause pointing at law 7. `LAWS.length` renders in the panel, so the count follows the array. **Any change to a form mechanism means editing `LAWS` in the same commit.**

Forms have now been through three arrangements: seven separate resolver knobs (`reach`, `laps`, `shortfall`, `transit`, `gaps`) with one law bent apiece and a `BEND_TOLL` for the bending; then cosmetic, with the seventh law deleted; now two shared mechanisms plus elegy's capped grief. Do not add further per-form knobs — the point of this arrangement is that a form is a *choice of setting*, not a branch in the resolver.

### Caster level

A working has a level, 1 through 5, stored on the spell itself (`Spell.casterLevel`) and set directly through `LevelControl` in the editor rather than earned — there is nothing in this app that tracks actions to award experience for, and a reference codex suits a stat you declare over one you grind. `WorkshopProvider` threads `draft.casterLevel` into `computeReaction` as the third argument, so raising it in the editor re-resolves the ring exactly as changing the form does.

**Level belongs to the spell, not the caster.** It lived on the user profile at first, one number shared by every working, and that was the bug: raising it to grow one spell silently re-resolved every other saved spell too, since they all read the same profile value. A spell tuned and fed at level 2 could come back underfed or overflowing after the profile was raised to level 4 for an unrelated working, with nothing about that spell having changed. Moving the field onto `Spell` means a working resolves the same way every time it is opened, and the only way to change that is to open its own editor and move its own `LevelControl` — `normalizeSpell` defaults a spell written before this field existed to `DEFAULT_CASTER_LEVEL`, the same read-and-write-side normalization pattern as a component's ledger.

**Level scales what a reagent demands and what it yields, together and by the same fraction — the eighth law.** `LEVEL_POWER` is the table: 1 → 40%, 2 → 55%, 3 → 70%, 4 → 85%, 5 → 100%. A level-one working is reading a smaller reagent, not a penalized one, and the five steps are a plain 15 points apart with the ceiling landing on exactly the whole catalog rather than some fraction of a "true" number — there is no number a reagent's ledger is scaled down *from*.

**The flat transit cost scales down with level too, on its own shallower curve.** `TRANSIT_POWER` reaches 1 (full, catalog-scale cost) by level 4 rather than needing level 5: 1 → 55%, 2 → 70%, 3 → 85%, 4 → 100%, 5 → 100%. The completion spill does not move with level at all — only the lap's flat cost gets its own discount, and a smaller one than the reagents get. This is a reversal of an earlier design, recorded below, and it exists because the earlier one was too punishing at the bottom: with transit held flat, a level-one working's reagents shrink to 40% of the catalog while the lap still costs its full, unscaled 16 units, and a *fed* ring — one built so nothing starves — still came up empty 85% of the time, even placed with total care. `TRANSIT_POWER` closes most of that gap without closing all of it: at level one a reagent is at 40% strength against a lap at 55% of its cost, so the lap is still proportionally dearer than the reagent feeding it, which is what keeps level one harder than level five rather than merely smaller. See the by-level table below for what the two curves together actually buy.

**Getting the fraction to round into an actual integer crossing cost took a second fix.** `TRANSIT_LOSS_REAGENT` is 2, so multiplying it by a level's fraction and rounding leaves almost nowhere to round to — `TRANSIT_POWER[1]` and `TRANSIT_POWER[2]` both round to 1, `TRANSIT_POWER[3]` and `TRANSIT_POWER[4]`/`[5]` both round to 2, collapsing five levels onto two possible lap costs. Rounding once per spell rather than once per crossing does not fix this, only moves where the collapse happens. `crossInto` in `lib/reaction.ts` instead carries the fractional remainder from one crossing to the next — a crossing's exact cost is added to a running carry, the carry rounded to the nearest unit is what gets charged, and the difference carries forward — so a lap's total cost tracks the exact rate to within one unit and varies continuously across levels rather than jumping between two values. One carry serves both reagent and gap crossings; gap cost is exactly double reagent cost before rounding, so the ratio holds on average across a lap rather than on every single crossing, the same tolerance `spendProportional`'s `Parcel.debt` already relies on for the proportional toll.

Two other shapes were tried first and dropped, for reasons worth recording so they are not tried again the same way:

- **Locking forms behind level** — invocation at level five, prayer at level one, and so on. Rejected because it front-loads the weak forms and back-loads the strong ones for no reason the ring itself gives: a form's condition is a fact about the ring's shape, not about the caster, and gating it by fiat reads as an arbitrary rule bolted on top rather than something the circle demands.
- **A flat discount on transit loss by level, at the same rate `LEVEL_POWER` uses.** Rejected the first time because it overlaps with what skilled play already buys and narrows the skill gap instead of widening it. `TRANSIT_POWER`'s shallower curve is a version of this same idea revisited, not a reversal of the reasoning: it never discounts transit as much as it shrinks the reagent paying for it, so the widening gap the original rejection was protecting survives (see the table below), while the level-one floor that made a fed ring dead 85% of the time does not.

**The catalog and the flat transit cost were both doubled, together, in the same change** (`data/seedComponents.ts`, `SEED_VERSION` 9; `TRANSIT_LOSS_REAGENT`/`TRANSIT_LOSS_GAP` and `MAX_LEDGER_ENTRY` in `types/worldbuilding.ts`). Doubling only the catalog was tried first, and it is wrong, for a reason worth stating plainly: a low level needs headroom above the lap's flat cost or transit alone consumes it, but raising the ceiling *without* raising the lap's cost widens that headroom at every level, level five included — a single strong reagent could then clear a full lap with far more left over than before, which made a sparse ring disproportionately rewarding at full power. That is exactly backwards: width is supposed to be the only way to real output, and doubling only the catalog made it easier to skip, not harder, the higher the level. Doubling the transit constants alongside the catalog restores the *original* ratio between a reagent's ceiling and the lap's cost — 24:16 is the same 1.5 the old 12:8 was — so a level-five caster's sparse-ring math is unchanged from before either constant moved; only level one, reading a shrunken catalog against this same larger lap, gets the numerical room it needed. The circle table below confirms it: every reagent count grew almost exactly ×2 from the pre-doubling numbers, not more at the sparse end — a uniform rescale changes no ratio the resolver computes.

Verified against the harness (`levelReport`, full ring, level held constant per row):

| level | power | manifestation | toll | fed manifestation | fed rings delivering nothing |
| --- | --- | --- | --- | --- | --- |
| 1 | 40% | 20.3 | 27.0 | 2.0 | 41% |
| 2 | 55% | 29.3 | 37.1 | 4.5 | 24% |
| 3 | 70% | 36.7 | 45.8 | 7.8 | 9% |
| 4 | 85% | 44.9 | 55.4 | 8.2 | 12% |
| 5 | 100% | 54.0 | 63.9 | 11.8 | 10% |

Levels four and five's plain `manifestation`/`toll` columns are still close to unchanged from before `TRANSIT_POWER` existed — both already paid the lap's full cost — confirming the curve and the carry touch nothing above where they're supposed to. The `fed` columns tell a different story than they used to: TRANSIT_POWER originally closed the level-one fed-dead rate from 85% down to 1%, with the rest of the table at 0%; the one-source cap above reopened part of that, since a fed ring's builder could no longer paper over a hard-to-feed low-level ring with a spare source, and every level now shows some fed-dead rather than only the bottom one — level five, which had read 0% through every earlier version of this table, now reads 10%. That is the harness's construction gap described under "Balance" (`growFed` is a one-pass walk that can dead-end even when a fed ring exists), not evidence that a single-source fed ring is out of reach at these levels; it says the naive greedy-plus-retry search converges less often, most at the bottom of the level range where there is less room to be wrong. Careless play's net (manifestation minus toll) stays modestly negative at every level (−6.7 at level one, −9.9 at level five); a fed ring's net (toll is always zero once fed) runs 2.0 to 11.8 across the same range. The *gap* between the two still widens with level (8.7 at level one to 21.7 at level five), which is the property that matters — building the ring well pays off more at the top than the bottom — even though the one-source cap pulled both ends down from where they read before it. `measuringFormsNeverChargeAcrossLevels` asserts the three measuring forms still charge nothing at every level, not only at the level-five default the rest of the harness runs at.

### Balance

`sim/balance.ts` checks two separable things: the circle, and the forms. `sim/generateNearOptimal.ts` hill-climbs a true frontier per form — 10 rings each, honoring law 5 throughout the climb, kept in `sim/nearOptimalRings.ts` — which is what caught the litany/benediction loophole below: `fedRing`'s "starves nowhere" bar and the random sampling elsewhere in this file are both too coarse to notice a condition a genuinely optimizing caster has no reason to meet. `balance.ts --near-optimal` resolves just that curated set and skips the slow sampling, for a fast read after a form's condition changes.

**The circle** is measured under the prayer, the one form that asks nothing and spares nothing, so these numbers stay directly comparable across form changes — a change that moves the prayer has moved the circle. Law 1 on every ring and under every form (`manifestation + bled + drawn === released`, thrown on rather than reported), the shape of output against reagent count, that every currency still reaches the mouth, and a paired probe for the relay condition. Measured at caster level five (full power) — level is a separate axis, covered above. Over 136k rings — random and source-first, plus a "fully fed" builder that only places a reagent if the ring still starves nowhere:

| reagents | manifestation | toll | bled | dead rings |
| --- | --- | --- | --- | --- |
| 2 | 2.3 | 25.4 | 24.1 | 25% |
| 4 | 13.3 | 44.0 | 32.8 | 1% |
| 6 | 31.3 | 56.1 | 26.8 | 0% |
| 8 | 53.9 | 64.1 | 12.5 | 0% |

These are almost exactly the pre-doubling table (1.2 / 6.9 / 15.9 / 27.7) at ×2 — 1.92×, 1.94×, 1.99× and 2.00× respectively — which is the point of doubling the catalog and the flat transit cost *together* rather than the catalog alone. A uniform rescale changes no ratio the resolver computes, only the absolute numbers. Two reagents' dead rate (25%) sits close to both the pre-doubling number (31%) and the older pre-August-2026-retune number this row is descended from (2.2 / 11.0 / 25.0 / 43.4, 28% dead at two reagents) — thinning the free reagents and pricing most conversions underwater in August 2026 already did the work of keeping a sparse ring fragile, and this rescale doesn't undo it.

The one-source cap moves this table by a percent or two at most (8-reagent manifestation 55.4 → 53.9, toll 62.3 → 64.1): a careless or "source-first" ring drawing a *second* source by chance was already rare at these widths, so random and built play barely notice the rule. Its bite is on the ceiling below — see "fully fed" — where a caster was deliberately stacking sources rather than stumbling into one.

An earlier version of this same change doubled only the catalog and left transit at its old, now-comparatively-tiny cost. That produced growth concentrated at the sparse end (up to 3.25×, against a uniform ~2× everywhere once transit was scaled to match) and a two-reagent dead rate of 7% instead of 25% — a single strong reagent could clear a full lap with room to spare, which made a two-reagent ring disproportionately rewarding at full power, the opposite of what width is supposed to guard against. See "Caster level" for the full story.

Five things to look at when the numbers move:

- **Output is superlinear in reagents** — a full ring beats two half rings, which is what makes slot order a craft rather than a chore.
- **A fully fed eight-reagent ring makes 17.7 and pays 0, against a random one's 53.9 and 64.1.** That ceiling dropped from 31.9 with the one-source cap — a fed ring's builder (`fedRing`/`growFed` in the harness, `placeComponent` in the app) could previously lean on a second or third source to guarantee every slot fed, since a source can never itself go short and only ever adds current; with one source allowed, feeding every slot from a single supply is a genuinely harder placement problem, not just a smaller number. Random still clearly loses on raw output to fed's toll of zero, which is the point of the August 2026 retune, and that hasn't moved. If fed rings start winning on output outright, the tuning has collapsed the other way.
- **Every currency stays between 15% and 25% of everything delivered.** A currency drifting toward zero means a seed's ledgers were retuned without re-checking the frontier.
- **`naiveChainProbe`'s toll-free rate must stay well under 50%.** It is the harness's model of a player who never looks further back than the slot immediately before the one they are filling; before the August 2026 retune it printed 100% at a manifestation matching `fedRing`'s own deliberate search, which meant reading only the last card placed was a complete strategy. It now prints 0%.
- **The two relay checks and the transit payer, all hard assertions rather than readings to interpret.** `the relay crossing` must print `OK`. It probes with two synthetic reagents demanding `MAX_LEDGER_ENTRY` — a fixed ceiling rather than a catalog reagent's own yield — so the received amount is never capped by the demand and the probe can't be thrown off by a future catalog retune the way pinning it to a specific source's yield would; the assertion itself reads `TRANSIT_LOSS_REAGENT` off the constant rather than hard-coding the gap between the two, so it survives a retune of the transit cost too. It is pinned to the prayer, since a form sparing the transit makes relay and reagent cost the same — correct behaviour, useless as a probe. `padding a sparse ring with two isolated relays` must print `0/4000 OK`, meaning no ring lets a starved relay raise the manifestation without paying for it. `the transit payer` must print `OK` twice: a chain fed across two holes receives the same whether or not an unrelated source stands at slot I, and a lone source's lap is charged in full. That last check compares the loss against the lap's fixed flat cost (`(RING_SLOT_COUNT - 1) * TRANSIT_LOSS_GAP + TRANSIT_LOSS_REAGENT`) rather than demanding literally every unit vanish — the two happen to coincide for every reagent in the current catalog, since nothing yields enough to outrun a full lap at this scale, but the assertion is written to stay correct even if a future reagent's yield ever did.

**`growFed` needed a matching change, and the fix is only partial.** It builds a "fed" ring one slot at a time, taking the first candidate that leaves every already-placed slot starving nowhere — before the cap, a second or third source was always such a candidate, since a source can never itself starve, so `growFed` leaned on it as a safe filler whenever the right fuel or converter wasn't obviously next. With sources capped to one, that filler is gone and the same one-pass, no-backtracking walk can dead-end partway through a ring a smarter ordering would have completed; `fedRing`/`fedRingIn` now retry with a fresh shuffle (`FED_ATTEMPTS`, 30) rather than accept a stunted partial ring, but this brings the dead rate down, not to zero — see the by-level table below, where level 5's fed-dead climbs from 0% to 10%. A full ring built from one source and seven others *does* still resolve toll-free (a direct search over the whole remaining pool at each slot finds one at 46 manifestation without needing to retry at all), so this is a harness convergence gap, not a claim that a single-source fed ring is now rare in practice — a real player, unlike a blind one-pass shuffle, is not throwing away a placement the moment it fails a local check.

Note that bled *falls* as the ring fills (33.1 at four reagents, 12.5 at eight) even though a fuller ring is a longer walk. That is the completion spill in law 4, not transit: a four-reagent ring throws away roughly half of what it still holds at the mouth. Transit itself is at most 16 units a lap under a prayer at this catalog's scale. Bled at eight reagents (12.5) moved almost exactly ×2 from the pre-doubling figure (6.3) — as it should, now that transit was doubled along with everything else; an earlier version of this change that doubled only the catalog left this number nearly flat (a full ring never spills, so its bled figure there was almost entirely the old, unscaled transit cost).

**The forms** get three more checks, and two hard assertions:

- **A measuring form must never charge.** Thrown on, over every ring in the sweep.
- **Every form must win somewhere.** Two objectives, because there is no single one: `loud` (most delivered) and `cheap` (best on manifestation minus toll). Read `cheap` with care — it prices a unit out of the caster exactly like a unit delivered, so doing nothing scores well, and a measuring form taking `cheap` on a ring it delivered 1.0 on is not a win in any sense a player would recognise.
- **Each form against the prayer on rings that answer its condition**, in two cohorts, and the pair is the point:

| form | fed: own | fed: prayer | careless: own | careless: prayer |
| --- | --- | --- | --- | --- |
| litany | 26.9 | 20.4 | 50.9 | 42.8 |
| dirge | 20.1 | 4.9 | 44.3 | 29.6 |
| invocation | 36.0 | 21.9 | 64.9 | 56.8 |
| ward | 19.3 | 12.0 | 2.3 | 20.6 |
| benediction | 21.1 | 1.5 | 8.9 | 2.4 |
| elegy | cannot be fed | — | 29.7 | 8.6 |

The `fed` columns fell across the board with the one-source cap (litany's own-ground figure roughly halved, 32.5 → 16.5), and both litany's and benediction's climbed again once their conditions moved off `spill` alone (litany 16.5 → 26.9, benediction 3.2 → 21.1 — see "Eight things" above). `careless` moved far less for litany, but jumped for benediction (0.4 → 8.9): a `spill`-only benediction only ever mattered on the rare careless ring that happened to land at three reagents or fewer by chance, where `both` also pays out on any careless ring under the transit-sparing half. The comparison the pair exists for still holds regardless — every form still beats the prayer on ground it chose, fed or careless.

  **The fed cohort is the one to tune against.** On a fed ring the underfed rule cannot matter — `credit` and `measure` agree once there is no shortfall left to settle — so whatever separates a form's own resolution from the same ring's prayer is the condition's relief alone, and every form beats the prayer on ground it chose. Litany's own-ground edge no longer needs the caveat this table used to carry: under the old `spill`-only condition a spared spill was worth up to four times on a two-reagent ring but nothing on a full one, so the fed cohort's uniform sampling across ring width buried the edge under wide rings that happened to seat two relays while the spill relief they earned did nothing — a real artefact, not a weak form. `both` closes that: sparing transit pays on a full ring exactly as it does on a narrow one, so 26.9 against 20.4 is the honest edge now, not an average dragged down by a construction the caster was never rewarded for building. Litany's global `loud`/`cheap` rates (10%/3%) read lower than under the pure-`spill` condition (13%/3%) for the mirror-image reason: most random and built rings in that sweep don't happen to carry two relays, and failing the condition now costs the doubled transit too, not only the doubled spill — carelessness got more expensive, which is the point.

  The careless cohort is the same rings thrown together, where the average slot gets 38% of what it asked; a prayer's output there is almost entirely reagents firing on credit, which is exactly what its toll of 38-odd is buying. Ward and benediction reading 2.3 and 8.9 there is mostly the underfed rule showing up rather than a broken form: `measure` declines the same credit that is inflating the prayer's own number, so it has little to show and nothing to pay — benediction's own figure is higher than ward's here specifically because `both` now pays it out on any careless ring that happens to fall at three reagents or fewer, not only a deliberately built one. Dirge reads differently now that its own underfed setting is `credit` (see "Eight things" above) — 44.3 against a toll of 50.8, the same shape as the other crediting forms, because a dirge whose sink happens to be fed says nothing about whether the rest of the ring was, and `credit` bills it exactly like a prayer would. **An elegy can never be fed** — it forbids a source anywhere, so the first reagent the current reaches must starve. It always pays something, by construction, and the harness says so rather than reporting a failure — but since `loss: 'both'` (see "Eight things" above), that something is only ever the one starved slot's demand, never the lap's transit on top of it.

Conditions are found by rejection sampling against the real predicates in `FORM_META`, so shapes are never described twice and cannot drift. `fedRingIn` fills an arbitrary slot set, which `fedRing` cannot: `fedRing` lays reagents contiguously from slot I, and two conditions ask for shapes it never produces (elegy needs slot I empty, ward needs slot VIII filled with a gap short of it), which reports them unreachable when they are merely unbuilt. Litany used to be a third — the old paired-run shape needed gaps a contiguous lay can't leave — but a role instead of a shape has no position to fail on, so `fedRing` can seat it as easily as `fedRingIn` can.

## Firestore

```
users/{uid}                          -> { seedVersion, seededAt }
users/{uid}/components/{componentId} -> MaterialComponent (id stripped; document id carries it)
users/{uid}/spells/{spellId}         -> Spell (carries its own casterLevel)
```

`firestore.rules` restricts everything under `users/{uid}` to that uid. Ids are minted client-side (`lib/id.ts`).

Traps in `firestoreRepository.ts`:

- **StrictMode double-invokes the load effect.** Seeding claims its version marker inside a `runTransaction`, and `listComponents` de-dupes concurrent calls through an `inFlight` promise. Any new "write once on first load" logic needs the same treatment.
- **`SEED_VERSION` (currently 15) must be bumped whenever `seedComponents.ts` changes shape** — existing users never see the change otherwise. A new catalog installs *alongside* what the user has, never over it.
- **`Spell.casterLevel` defaults to 1 (`DEFAULT_CASTER_LEVEL`) for a spell written before the field existed**, via `normalizeCasterLevel` inside `normalizeSpell` — the same read-and-write-side normalization pattern as a component's ledger.
- **`loadComponents` is not read-only**: `pruneInert` deletes any component whose two ledgers are both empty, which is how pre-ledger leftovers get cleared.
- Firestore uses `persistentLocalCache` with multi-tab support, so the workshop stays readable and writable offline.

## Conventions

- **Context files are split three ways** — `fooContext.ts` (createContext + value type), `FooProvider.tsx`, `useFoo.ts` — to satisfy `eslint-plugin-react-refresh`. Keep the split when adding a context.
- **Ledgers are normalized on both read and write** (`normalizeLedger`, `normalizeComponent`, `normalizeSlots`), so hand-edited documents and records from older data models still load. Zero entries are dropped rather than stored, keeping documents small and free of `undefined`.
- **Persisted mutations go through `write()` in `WorkshopProvider`**: local state updates only after the write lands, and failures surface in `error` (rendered by `StorageAlert`).
- Styling is hand-written BEM in `src/App.css` (~1100 lines) over CSS custom properties in `src/index.css`. Both themes are defined there — light is "ink on parchment", dark is the same desk by candlelight — and every colour must be a token so both keep working.
- Comments in this codebase explain *why* a rule exists, especially where the reason is a balance decision or a Firebase quirk. Match that when touching `reaction.ts`, `currencies.ts`, or `firestoreRepository.ts`.
- Prose in the UI is in-world and deliberately specific (a spell is a prayer/elegy/litany; unmet demand is a toll paid out of the caster's body). New copy should be computable and stated, not evocative and vague.
- **Write succinct sentences and vary their structure.** The failure mode to avoid is corny: a colon-and-restatement in every line, a trailing subordinate clause explaining the thing that was just said, atmosphere welded onto a rule. "The spill is squared. Four reagents deliver a quarter, not a half." — not "Until it does, the spill is squared, and what reaches the mouth falls away with every hole." Say the mechanic, give the number, stop. Keep flavour and mechanics in separate fields where the data model allows it (`SpellFormMeta.gloss` vs `condition.statement`) rather than in the same sentence.
- **A thing standing in a slot is a *reagent*.** `MaterialComponent` and "material" are the formal names; "reagent" is the countable word prose uses — "an ordinary reagent", "eight reagents deliver all of it". It replaced "stone" (August 2026), which came from the ring being a physical circle and belonged to neither of the system's two metaphors: the ledgers are stoichiometry (law 1 is conservation of mass), while `current`/`source`/`fuel`/`relay`/`sink`/`transit` is a circuit. Note `Lodestone` is a catalog entry and `limestone` is flavour text — neither is the noun.
- **Prayer, elegy, litany, dirge, invocation, ward and benediction are collectively the *alchemical rites*.** `SpellForm`, `FORM_META`, `FORM_LIST` and "form" stay the code and UI vocabulary — the field label reads "Form", not "Rite" — since a player is picking a setting, not learning a new noun. "Rite"/"rites" is prose vocabulary for referring to the set or to one of its members in flavour text, the same relationship "reagent" has to `MaterialComponent`: alchemical for the mechanism the rites sit on top of (ledgers, conservation, toll), rite for the liturgical register each of the seven names already carries.

Run `npm run dev`, launch Edge (`C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe`) with `--headless=new --remote-debugging-port=9222 --user-data-dir=<temp>`, then drive it over raw CDP from Node (v22, global `WebSocket`) via `Page.navigate` / `Runtime.evaluate` / `Page.captureScreenshot`.

Gotcha: React has not re-rendered between two `.click()` calls issued in the *same* `Runtime.evaluate`. Arming a component and clicking a slot must be separate evaluates — otherwise the placement silently no-ops and it looks exactly like an app bug.
